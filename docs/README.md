# Documentation Map

This directory contains Curiofold's durable project knowledge.

The objective is to ensure that important requirements and decisions live in the repository rather than only in chat history.

---

## Structure

```text
docs/
├── README.md
├── product/
│   ├── ORIGINAL_BRIEF.md
│   └── PROJECT_SPEC.md
├── design/
│   ├── PRODUCT_DESIGN.md
│   ├── RESPONSIVE_CROSS_BROWSER_STANDARDS.md
│   ├── STORY_PDF_CREATION_STANDARD.md
│   └── STORY_PDF_DESIGN.md
├── project/
│   ├── DELIVERY_GOVERNANCE.md
│   └── OPEN_DECISIONS.md
├── engineering/           # created/maintained by Codex after approved planning
│   ├── EXECUTION_PLAN.md
│   └── STATUS.md
└── decisions/             # created/maintained by Codex
    └── ADR-xxxx-*.md
```

Do not create empty engineering documents merely to fill the tree. Codex should create them when the approved plan gives them real content.

---

# 1. Product documents

## `product/ORIGINAL_BRIEF.md`

The untouched original project overview supplied by the product owner.

Purpose:

- provenance;
- original intent;
- audit trail when later decisions evolve the concept.

Do not edit this file to reflect later decisions. Create/update the normalized specification instead.

---

## `product/PROJECT_SPEC.md`

The current normalized product/business contract.

It distinguishes:

- requirements directly supported by the original brief;
- product/design decisions adopted after analysis;
- known constraints;
- deliberately open decisions.

This is the primary product source of truth for engineering.

---

# 2. Design documents

## `design/PRODUCT_DESIGN.md`

Complete design source of truth.

Contains:

- working brand;
- visual identity;
- tokens;
- typography;
- navigation;
- UX flows;
- screen specifications;
- Reader behavior;
- credits UX;
- component/state requirements;
- responsive behavior;
- accessibility;
- content design;
- prototype requirements;
- design acceptance criteria.

The referenced approved Figma file is the visual authority when a visual detail differs from prose.

## `design/RESPONSIVE_CROSS_BROWSER_STANDARDS.md`

Authoritative frontend quality standard for responsive/adaptive behavior, supported browsers, inputs, viewport ranges, performance and cross-device validation.

Its PDF-viewer requirements are conditional: they apply if Curiofold later introduces an approved embedded PDF surface. They do not replace the current browser-native Reader decision in `PROJECT_SPEC.md` and `PRODUCT_DESIGN.md`.

## `design/STORY_PDF_CREATION_STANDARD.md`

Authoritative composition, flatplanning, preflight and quality-control standard for internal/export Curiofold Story PDFs.

## `design/STORY_PDF_DESIGN.md`

Authoritative visual/editorial design system for internal/export Curiofold Story PDFs, including typography, page geometry, visual truth, accessibility and paid-value gates.

PDF production remains an internal/export capability. The customer-facing v1 unit is a Story rendered in the responsive browser-native Reader; these standards do not authorize a public PDF URL, download flow or conventional PDF embed.

# 3. Project-delivery documents

## `project/DELIVERY_GOVERNANCE.md`

Defines how Codex should manage the project and Linear:

- hierarchy;
- Projects/Milestones/Issues;
- estimates;
- workflow;
- progressive elaboration;
- issue quality;
- dependencies;
- Definition of Ready/Done;
- updates;
- change management.

It is process policy, not software architecture.

---

## `project/OPEN_DECISIONS.md`

A living decision queue.

Only material unresolved choices should live here.

Each entry includes:

- decision;
- status;
- owner;
- when it becomes blocking;
- available context;
- eventual resolution.

Once resolved, record the result and link the durable destination such as the Product Spec or an ADR.

# 5. ADRs

Material technical choices belong under `docs/decisions/`.

Suggested naming:

```text
ADR-0001-application-architecture.md
ADR-0002-authentication-strategy.md
ADR-0003-content-rendering-model.md
```

Each ADR should capture:

- Context
- Decision
- Alternatives considered
- Consequences
- Status
- Date

Do not write ADRs for trivial implementation details.

---

# 6. Source-of-truth hierarchy

In case of conflict:

1. Later explicit product-owner decision.
2. `product/PROJECT_SPEC.md`.
3. `design/PRODUCT_DESIGN.md` + approved Figma for design behavior.
4. `product/ORIGINAL_BRIEF.md`.
5. Approved engineering plan / ADRs for technical implementation.
6. Linear for operational execution state.
7. Agent assumptions.

Material conflicts must be surfaced rather than silently reconciled.

---

# 7. Documentation quality rules

Documentation must be:

- current;
- specific;
- concise enough to maintain;
- linked rather than duplicated unnecessarily;
- explicit about status and ownership;
- factual about implementation state.

Avoid duplicating the same evolving technical fact in several files.

Prefer one canonical location and links from the others.
